What a receipt proves

Why ENS at all?

  • Canonical naming: judge-facing URLs and content hashes pinned to a domain you can resolve and verify.
  • Trust anchoring: ENS records point at the actual deployment, so trust lives in a verifiable registry, not in a marketing site.
  • Composability: ENS-aware agents and wallets can route to the right surface automatically.

The ENS repoint step (E1) is owner-only and is gated by the master plan: "ENS repoint (E1) human-only". No broadcast will be attempted from any subagent.

How it works

A judge-friendly explanation. Every layer in the diagram below is real on the workbench today, even if some are honest partials.

The flow

  1. User writes a prompt. The browser posts it to the public app origin.
  2. Capability handshake. The access package verifies provider pins (Ed25519 JWK), issues a short-lived capability.
  3. Provider selection. For non-economic flow, the loopback app picks a pinned provider; for paid flow, the app quotes an x402 payment (Hedera, 1 tinybar).
  4. Submission. The browser POSTs /v1/jobs with the capability. The app returns a 202 + job id.
  5. Native inference. The 0.5B Instruct model runs across two node processes, returning real token IDs.
  6. Stream. The app pushes SSE events: job, delta (with tokenIds), and done.
  7. Receipt. An Ed25519 receipt is written to core.sqlite; for paid, the Hedera transfer carries a memo ethonline:<requestHash>.
  8. Verification ledger. Audits, stake events, and provider claims are indexed on The Graph (Sepolia Registry / VerificationLedger) — currently schema-deployed with empty provider collections.
  9. Verifier (TEE). The ensemble verifier runs in a GCP Confidential Space SEV VM; /healthz and /info answer on 8765. If T6 is live on 8766, this UI separately detects /healthz, /attestation, and /generate-key.
  10. ENS discovery. Canonical surfaces are pinned to mycelium.now and verifier.mycelium.now; ENS broadcast is human-only (E1).
